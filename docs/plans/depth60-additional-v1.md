This plan precedes implementation. The user requested a few additional fast, inexpensive OpenAI models under a time constraint. All four receive the unchanged nine-case depth-60 suite and three fresh trials per case. Earlier two-model answers were already inspected; this is a separate exploratory follow-up, not held-out confirmation or a revised original population.

1. Preserve the original pilot's default API, commands, model IDs and artifacts through two fixed configurations in the existing operator. The additional requested IDs are `gpt-5.4-nano`, `gpt-5.4-mini`, `gpt-5.6-luna` and `gpt-6-luna`. Keep `one-shot-json-v1`, provider-default reasoning/sampling, 4,096 output tokens, existing prompt construction and standard 180-second inference/20-second metadata limits. Verify old identities and unchanged suite/prompt hashes.
2. Require the original pilot's complete terminal evidence: 54 unique model/case/trial rows, two complete 27-trial reports, actual retained sends and matching frozen source hashes. The unchanged prior lineage contributes 7,854 requests; the pilot adds 54, giving 7,908. A separately authorized depth-100 session adds 54, so the additional study must wait for that session's terminal 54 unique complete outcomes and bind its matrix/progress/result hashes. The coordinated prior is 7,962. Freeze exactly 108 new requests, giving at most 8,070 within 8,192 and leaving 122. Retain earlier unknown remote sends once. Verify missing, altered or incomplete prior evidence and changed budgets refuse admission.
3. Start four requests, one for each additional model. Increase concurrency to at most 12 only when every initial response reports at least 108 remaining requests and 100,000 remaining tokens; otherwise retain concurrency four. Use the existing SDK/inference path, with no setting probe, retry, substitution or replacement. Persist each dispatch's model/case/trial identity and request-body hash before transmission through a per-row inference closure. Verify exact 108 unique identities, limits and stop conditions with injected fixtures.
4. Preserve normalized outcomes and raw visible text privately, including failed, cancelled, absent and unknown evidence. Export partial summaries safely before an incomplete study exits unsuccessfully. No provider-envelope replay is claimed: the existing inference contract retains normalized evidence and assistant-visible text, not the complete raw HTTP response. Verify persistence and incomplete-publication boundaries without calling a provider.
5. Run focused old/new operator fixtures and API lint, type checking and build. Root owns any later freeze/live launch and independent arithmetic audit; the UI owner updates the landing table only from actual audited results. No credential read, inference request, API restart, database mutation, publication or commit occurs during implementation.
